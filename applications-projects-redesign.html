Applications & Projects — visual redesign

A consistent design language for the Applications and Projects sections, with rendered mockups and an implementation brief. Built to be handed to a code session for the Next.js + Tailwind codebase. No code in the app has been changed.

1 · Design system

These rules resolve the inconsistencies found across the audit (mixed primary-button colours, three stepper treatments, a zoo of badge styles, overused uppercase, and two unrelated progress-bar styles). Apply them globally first, then the per-screen changes fall out cheaply.

Brand tokens (already in globals.css)

forest #1f5c52
gold #e8a030
progress green #6aa84f
warm #e8ddd0
cream #faf7f2

Type: Space Grotesk for headings/UI, Plus Jakarta Sans for body — unchanged.

Accent colours are limited to forest, gold, and the progress green. Do not introduce sage/teal as an accent — it is not part of this palette.

Primary action — one colour

Exactly one filled primary per screen, always forest #1f5c52. Everything secondary is white with a 1px outline. The lime green is demoted to progress fills only — never a button. This kills the current lime/forest/outline button confusion.

Status badges — one system

Same pill shape (radius 6px, 12px / weight 600). Colour encodes meaning, applied everywhere (list rows, eligibility, match tiers, answer flags, question states):

Looks eligible Good match Ready to match Partial match 32 words over 14 placeholders 7 gaps to fix Not started In progress

green = good / eligible / done · gold = needs attention · red = blocking gaps · grey = neutral/not started.

Stepper — one pattern, both creation routes

The project-creation route currently has no stepper while the funder-form route does. Use the same numbered 1–2–3 stepper on both so the two flows read as one product. Spec shown on the wizard mockup below.

Progress bar — one treatment

Always a labelled inline bar: count on the left, percentage on the right, 6px track, green fill. Used identically in list rows, the editor header, and project "described" state. Retire the full-width top hairline.

Micro-labels — sentence case

Drop the uppercase section labels in the editor (WHAT THEY FUND, YOUR MATERIAL, TIPS TO IMPROVE, NEXT BEST FIX). Per the existing rule, uppercase is reserved for the match-module structural labels and calendar day headers only. Everywhere else uses sentence case.

List row & card rhythm

One row template across applications, projects and funder matches: icon/monogram → title + status badge → meta line → progress/score → chevron. Delete moves to hover-only. Cards: white, 1px #e8e1d4 border, radius 12px.

2 · Section architecture & creation funnel (decided)

Keep Projects and Applications as two distinct sections, framed as a sequence (define → write) — not merged. A project is "what I need funded" and spawns many applications ("the form for each funder"). Merging would bury the genuinely useful flat worklist of live applications, and break standalone applications (the funder-form route and general proposals).

Creation funnel — honest per-section buttons (retire the fork)

Today "New application" opens a fork where one card, "A project that needs funding", routes to /dashboard/projects/new and creates a project. The label says application; the outcome is a project — the single most confusing thing in the flow. Fix: "New application" → straight to the funder form; "New project" → the describe box. Each button does exactly what it says; remove the chooser fork.

Discovery via empty states + cross-nudge

Move the guidance the fork used to provide into empty states: the Applications empty state carries "Applying to more than one funder? Start with a project →"; the Projects empty state explains describe-once-apply-many. Keep a persistent one-line cross-nudge on the Applications list even when populated, and a "save this as a reusable project?" prompt on a standalone application. (Protects against users skipping projects.)

Back-link — do this as well

Project → "Applications from this project" already exists. Add the reverse: an application shows "Part of: [project name]" with a link back. Turns two flat lists into a navigable hierarchy.

Keep shared layout, differentiate content

Do not diverge the two landing-page layouts — the shared row template is a learnability asset (learn it once, applies to both). Differentiate via content/foregrounding (the stat tiles already do this), not layout.

SCREEN 6

Application answer editor — three states

/dashboard/applications/[id] · per question
  • Lead with the draft action. When an answer is empty, the empty textarea is replaced by a "Start with a draft" panel: primary "Draft a starting version" button, the 3-step path (Draft → Review & check → Make it yours), and "write it from scratch" as a quiet secondary link. Icon is ti-file-pencil (document + pencil) — not sparkles/wand.
  • Score/tips panel is inert until there is content — no premature "Check this answer" on an empty answer; it reads "appears once you've drafted or written".
  • After drafting: the draft fills the editor with a "Draft — review and make it yours" badge; primary action becomes "Check this answer"; "Redraft" sits alongside; editing happens directly in the box.
  • After checking: score chip and ring are tier-coloured (4.5/10 = amber chip, coral ring — not green), with a one-line reason ("capped by an unresolved placeholder").
  • Link flags to the text. "Jump to next fix (n of m)" steps through gaps; placeholders render inline in the answer as a highlighted gold block ("needs your input"), instead of raw **markdown** at the bottom.
  • Sentence case throughout (your answer, tips to improve, next best fix, guide). A step indicator shows where the user is in the flow.

4 · Follow-up improvements (post-implementation)

Tweaks on top of the shipped landing pages. Same routes: /dashboard/applications and /dashboard/projects.

"How it works" — fix step-number contrast

The shipped step badges use a pale green number on a pale green circle and are nearly invisible. Make each badge a filled forest circle (#1f5c52) with a white number, and connect the steps with a thin #e3efe9 rule so they read as a sequence. Drop the per-step bordered card — the row of connected badges is enough. (Rendered mockup provided separately.)

Row delete icon — hover only

The trash icon is always visible on each row. Show it on row hover/focus only; the chevron already signals interactivity. Reduces noise and accidental-delete risk.

Third stat tile — make it earn its place

"1 Project" / "1 Application" just restates the row count. Replace with an actionable count, e.g. Applications: In progress · Submitted · Deadline soon; Projects: Ready to match · Funded · In draft.

Progress-bar label parity

The Applications row shows progress context inline ("4 of 9 written"); the Projects row's bar shows only "90%". Add "90% described" so both bars read identically.

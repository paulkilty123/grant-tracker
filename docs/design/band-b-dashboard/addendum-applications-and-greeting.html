Applications fallback, and the greeting

Your §0a finding kills the second line I designed. Here's what the row does instead — and why it shouldn't announce the missing project.

Don't render "No project assigned" — it's true of every row

My earlier mockup styled one unassigned application as a grey tile with that label, on the assumption it was an outlier worth flagging. It isn't an outlier: it's 100% of applications, for structural reasons. A warning that fires on everything isn't a warning, it's chrome — and it would tell every user, on every row, about a gap they can't close because there's no picker to close it with.

So the fallback says nothing about projects at all. The project colour system in §4 goes dormant — not deleted. The row keeps a second-line slot; when project_id starts populating, the project name and its colour fill it and the tile stops being neutral. Nothing about the layout changes on that day.

Two rules that come with the fallback

Sort by updated_at, newest first, within each group. Without projects, recency is the only ordering that carries meaning — and it's the one that matches what the card is for, which is resuming work. It also makes the timestamps do double duty: they disambiguate and they explain the order.

Show funder_name only when it differs from grant_name. `WorkApp.funder` at :215 already does exactly this — it's set only when both exist. Right rule, currently feeding nothing but a monogram.

Relative dates under a week, absolute beyond. "Edited 2 days ago" is more useful than a date when it's recent; "started 9 Aug" is more useful than "16 days ago" when it isn't.

The greeting — use the richer score for the copy, not for the gate

Agreed on canRunMatching, and agreed on not unifying: flipping 40 of 41 orgs out of "matches ready" to fix a sentence would be a bad trade.

But the fix for the user-visible half is already in the codebase. Keep canRunMatching as the gate and use matchProfileScore for the message. Same two-field test decides whether matching runs; the seven-field score decides what the page claims. Nothing flips state, and the sentence stops overstating.

Today — shown at 57%
Good evening, Paul.
Your profile's complete — time to find some funding.
Proposed — high score
Good evening, Paul.
377 opportunities scored against your profile.
Proposed — below ~70%
Good evening, Paul.
377 opportunities scored so far. Filling in the rest of your profile will sharpen them.

Neither version claims completeness. The low-score variant turns the gap into an offer rather than a warning — which matters, because at 57% the matching genuinely is running, it's just running on less than it could.

What I'd change in the spec as a result

§3, Your applications: second line is funder + timestamp, not project. Sort by updated_at desc within group.

§4, project colours: marked dormant. Tiles are --warm-neutral until project_id populates. The fixed hue order and the never-cycle rule stand for when it does.

§4, last paragraph: delete it. It says an application with no project is "probably a data problem worth reporting rather than styling politely" — which was right about the cause and wrong about the remedy. The dashboard is not where that gets reported.

§0b: resolved — rename, plus the greeting copy above.

New, outside Band B: the missing picker in the application creation flow. Worth its own note so it doesn't live only in this conversation — it's a product gap, not a design one, and every application created between now and the fix will have the same hole.

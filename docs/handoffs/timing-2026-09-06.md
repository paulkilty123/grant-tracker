# Handoff: timing on 187 live rows

Written 2026-09-06 by the orchestrating session for an Opus 5 session to run.
Launch is in four days. Read `CLAUDE.md` first, all of it. Then this.

## The job in one sentence

187 live rows show a fundraiser no timing at all: no deadline, not rolling, no
next open date. Read each funder page and record which of the three it is,
with the page's own sentence as the citation. Where the page states nothing,
change nothing.

The row list is `docs/handoffs/timing-rows-2026-09-06.json` (166 grants, 9
programmes, 8 in-kind, 4 investment). Work it top to bottom in batches of 20.
Do not touch any row not in the list.

## What a fundraiser must be able to tell from the row

State the check as a sentence about the user: "a fundraiser landing here can
tell whether they can apply today, and if not, when". The four states that
answer it, and the columns that encode each:

| the page says | write |
|---|---|
| applications accepted at any time, no closing date, "rolling", "ongoing", "apply anytime", "decisions quarterly" with no cut-off | `is_rolling: true`, `deadline: null` |
| a dated closing date in the future | `deadline: 'YYYY-MM-DD'`, `is_rolling: false` |
| closed now, reopens on a stated date or month | `is_rolling: false`, `deadline: null`, `next_open_date: '<the sentence>'`, `next_open_date_parsed: 'YYYY-MM-DD'` (first of the month if only a month is given) |
| recurring rounds with fixed dates each year | `deadline` = the next one, plus `deadline_cycle: [{day, month, label}]` for the pattern |

**Closed with no reopening date is not one of the four.** That is a different
problem (the row may not belong live) and is reported, not written. Same for
"by invitation only", "no unsolicited applications", "fund has closed": list
them in the results file under `report` with the quote, and leave the row.

A closing date in the past is never written. If the page's only date has
passed and nothing says a next round, that is "closed with no reopening date".

## Rules that are not optional

1. **Every write carries a quote that appears on the page.** The checker
   later confirms the quote against the page text. A paraphrase fails it.
   Copy the sentence, including the date, as the page prints it.
2. **Read the page, not the brief.** `funder_brief.decision_timeline` in the
   JSON is a hint about where to look, written by a model months ago. It is
   not evidence. Several rows carry a brief that contradicts the page.
3. **Read with curl and a browser user agent** (the pattern is in
   `scripts/who-can-apply-2026-09-05.ts`'s history: fetch, strip tags, grep).
   A 403 or a JS-only page goes in `report` as `unreadable`; do not guess.
   Do not call the Anthropic API for any of this. No `@anthropic-ai/sdk`
   import, no `/api/admin/enrich-grant`. Zero model spend is the budget.
4. **The apply_url may not be the fund's page.** If it is a homepage or an
   index, follow the link to the fund's own page and cite that URL in the
   citation's `source_url`. Bank it in `grant_sources` too (see the script
   template). Do not change `apply_url` in this job.
5. **Source is `user_verified:timing-2026-09-06`.** Never `admin:`. If
   `mergeGrantUpdate` refuses a field as pinned, log it under `report` as
   `pinned` with the quote and move on. A pinned value is Paul's and only he
   changes it.
6. **Dry run first, every batch.** The script prints what it would write;
   read the printout against the quotes before `--apply`.
7. **Prove the count.** After each batch, run the SQL below. The number must
   fall by exactly the rows you wrote. If it does not, stop and find out why
   before the next batch.

```sql
select count(*) from scraped_grants
where is_active and pipeline_state='published'
  and deadline is null and not is_rolling and next_open_date_parsed is null;
```

8. **Commit after every batch**, script and results file together, and push
   to `main`. These are data scripts, admin-only, so they merge on green
   without asking. Commit messages end with the attribution block CLAUDE.md
   gives, and the message goes in a file (`git commit -F`), never `-m` with
   quotes in it.

## The script shape

One script per batch, `scripts/timing-batch-NN-2026-09-06.ts`, in the shape
of `scripts/live-and-wrong-2026-09-05.ts`: a `ROWS` array of `{ id, title
regex, fields, citations }`, a title check that throws on a wrong row, dry
run by default, `--apply` to write, and `mergeGrantUpdate` for every write.

```ts
{ id: '…', re: /Funder name/,
  fields: { is_rolling: true, deadline: null,
    grant_sources: [{ url: '<page read>', label: 'Fund page (timing), read 2026-09-06', added_at: '2026-09-06' }] },
  cits: { is_rolling: { snippet: 'Applications are accepted throughout the year', confidence: 'high', source_url: '<page read>' } } }
```

Citations key on the column written: `is_rolling`, `deadline`, or
`next_open_date`. One quote per column.

## Results file

`docs/handoffs/timing-results-2026-09-06.json`, appended per batch:

```json
{ "batch": 1, "written": [{ "id": "…", "state": "rolling|dated|reopens|cycle" }],
  "report": [{ "id": "…", "why": "unreadable|not_stated|closed_no_date|invite_only|fund_closed|pinned", "quote": "…", "url": "…" }] }
```

`not_stated` needs the closest sentence the page has about timing, so the
reviewer can see that it was looked for.

## What the orchestrating session checks afterwards

A sample of ten written rows re-read against their pages; the count SQL
re-derived; the checker (`/api/cron/verify-rows?ids=…&run=true`) run on the
written rows so `field_evidence` confirms or contradicts each quote. Rows the
checker contradicts are reverted, so a wrong quote costs more than a skipped
row. When unsure, report rather than write.
